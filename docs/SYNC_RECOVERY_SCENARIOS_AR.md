# مصفوفة سيناريوهات المزامنة والاستعادة في MYFI

هذه المصفوفة هي عقد سلوكي للبرنامج. القاعدة الأساسية: لا نحذف بيانات بصمت، ولا نخلط بيانات حسابين، ولا نعتبر الهاتف الأوفلاين مصدراً أقل أهمية من الهاتف المتصل.

## الحالة الأساسية

- لكل حساب مساحة عمل مستقلة مرتبطة بمعرّف المستخدم.
- كل هاتف يحتفظ بنسخته المحلية المشفرة وبآخر نسخة مشتركة `base`.
- عند عودة الاتصال، يقارن الهاتف نسخته المحلية والنسخة السحابية مع `base` ثم يدمج التغييرات.
- الإضافات المستقلة تتحد، والحقول المختلفة في السجل نفسه تتحد، والتعارض الحقيقي يسجل ويعرض للمستخدم.
- سياسة حذف سجل مقابل تعديله حالياً: الحذف يفوز، مع تسجيل التعارض. هذه السياسة يجب اعتمادها أو تحويل الحذف إلى أرشفة قبل الإصدار الرسمي.

## الهواتف والاتصال

| السيناريو | النتيجة المطلوبة |
|---|---|
| هاتف A متصل، هاتف B أوفلاين، A يضيف حركة ثم B يضيف حركة | عند اتصال B تبقى الحركتان، ولا تستبدل إحداهما الأخرى. |
| الهاتفان أوفلاين ثم يضيف كل واحد سجلاً جديداً | اتحاد السجلين عند أول اتصال. |
| الهاتفان يعدلان حقولين مختلفين في الحركة نفسها | الاحتفاظ بالتعديلين. |
| الهاتفان يعدلان الحقل نفسه | اعتماد قيمة الهاتف الذي ينفذ الدمج مع تسجيل المسار والقيمة المتعارضة. |
| هاتف يحذف سجلاً والهاتف الآخر يعدله | الحذف يفوز حالياً، ويظهر كتعارض مسجل. يفضل مستقبلاً عرض خيار استعادة/أرشفة. |
| الهاتفان يحذفان السجل نفسه | يبقى محذوفاً بلا تعارض جديد. |
| الهاتفان يضيفان دفعة مختلفة للدين نفسه | تندمج الدفعتان حسب معرف الدفعة. |
| الهاتفان يضيفان سجلاً جديداً بالمعرف نفسه بسبب استيراد أو نسخة قديمة | لا يسمح الدمج بتكرار صامت؛ يجب مراجعة السجل المتعارض قبل الإنتاج. |
| اتصال ينقطع أثناء الرفع | تبقى `dirty` مفعلة، ويعاد الرفع عند المحاولة التالية. |
| جهاز آخر يكتب بين القراءة والرفع | يعاد السحب والدمج حتى أربع محاولات، ثم تبقى البيانات محلية مع رسالة أن إعادة المزامنة مطلوبة. |
| إغلاق التطبيق بعد تسجيل تغيير أو قبل اكتمال الرفع | التغيير محفوظ محلياً، ويعاد رفعه بعد فتح التطبيق والاتصال. |
| ساعة الهاتف خاطئة | رقم الإصدار السحابي هو المرجع للمزامنة، وليس ساعة الجهاز. |
| دخول الهاتفين للحساب للمرة الأولى بلا `base` | تدمج البيانات الموجودة بدلاً من استبدال أحد الهاتفين، ثم تنشأ قاعدة مشتركة جديدة. |

## الخروج والدخول والحسابات

| السيناريو | النتيجة المطلوبة |
|---|---|
| تسجيل الخروج مع تغييرات غير مرفوعة | تبقى التغييرات في مساحة الحساب المحلية، ولا تتحول إلى بيانات حساب آخر. |
| تسجيل الخروج ثم إدخال بيانات كضيف ثم تسجيل الدخول للحساب نفسه | تظهر مطالبة نقل بيانات الضيف؛ لا تحذف بيانات الضيف تلقائياً. |
| حساب مسجل فيه بيانات + ضيف فيه بيانات | يدمج الضيف مع الحساب مع إعادة توليد المعرفات المتصادمة وربط المحافظ والحركات. |
| الحساب فيه محفظة برصيد افتتاحي فقط + بيانات ضيف | يعامل الحساب كحساب مستخدم فعلي، وتندمج بيانات الضيف بدلاً من استبدال المحفظة. |
| رفض نقل بيانات الضيف | تبقى بيانات الضيف محفوظة ويمكن عرض المطالبة لاحقاً. |
| تسجيل الدخول بحساب مختلف | يفتح مساحة مختلفة تماماً؛ لا تظهر حركات الحساب السابق. |
| هاتفان يدخلان ببيانات ضيف ثم يسجلان الدخول للحساب نفسه | تدمج بيانات الضيفين، ويعاد حل المعرفات قبل الرفع. |
| خروج المستخدم أثناء عملية مزامنة | يجب إلغاء الرفع أو ربطه بالجلسة القديمة؛ يمنع كتابة بيانات الجلسة السابقة في حساب جديد. هذه حالة تحتاج اختبار جهاز حقيقي. |
| حذف التطبيق ثم إعادة تثبيته وتسجيل الدخول | تستعاد النسخة السحابية إن وجدت؛ وإن لم توجد، يستورد المستخدم نسخة `.myfi`. |

## النسخ والاستعادة

| السيناريو | النتيجة المطلوبة |
|---|---|
| تلف النسخة المحلية الحالية | محاولة استرداد آخر ثلاث نسخ محلية، مع إظهار رقم النسخة المستردة. |
| تلف النسخة الحالية وكل النسخ المحلية | لا يبدأ التطبيق ببيانات فارغة بصمت؛ يظهر خيار إعادة المحاولة أو الاستعادة من ملف. |
| استيراد ملف صحيح والجهاز أوفلاين | تستبدل البيانات المحلية بعد التحقق، وتبقى معلقة للمزامنة. |
| استيراد ملف صحيح والجهاز أونلاين | يحفظ محلياً ثم يمر عبر نفس مسار الدمج السحابي، ولا يستبدل بيانات جهاز آخر بصمت. |
| كلمة مرور خاطئة لملف مشفر | يرفض الفتح ولا يغير البيانات الحالية. |
| ملف معدل أو checksum غير صحيح | يرفض الملف قبل قراءة البيانات. |
| ملف من إصدار أحدث | يرفض الاستيراد مع رسالة أن التحديث مطلوب. |
| ملف احتياطي فارغ | يسمح به فقط كتغيير مقصود، ولا يمسح السحابة تلقائياً من دون مسار تأكيد واضح. |
| فشل الاستعادة بعد تغيير محلي | يرجع إلى الحالة السابقة ويحافظ على النسخة الاحتياطية المختارة. |

## الالتزامات والديون والأهداف

| السيناريو | النتيجة المطلوبة |
|---|---|
| هاتف A يؤجل الالتزام، وهاتف B يدفعه | لا ينشأ تكرار؛ الدفع يغلق الدورة الشهرية، والتأجيل لا يحول الالتزام إلى التزام يومي. |
| تأجيل الالتزام من آخر يوم في الشهر إلى الشهر التالي | يبقى محسوباً على دورة الشهر الأصلية ويظهر في تاريخ التأجيل الصحيح. |
| دفع الالتزام بعد التأجيل من هاتف أوفلاين | عند الاتصال تندمج حالة الدفع مع باقي البيانات ويختفي الاستحقاق من الدورة المدفوعة. |
| دفع الدين من هاتفين بدفعتين مختلفتين | تجمع الدفعتان، ولا يتجاوز المدفوع إجمالي الدين. |
| إكمال الدين أو الهدف | ينتقل إلى السجل/الأرشيف مع رسالة توضح أنه انتهى، ولا يعود للاستحقاقات النشطة. |
| أرشفة متابعة على هاتف واستمرار حركة مالية مرتبطة بها على هاتف آخر | تبقى الحركة في التاريخ، ولا تعيد المتابعة إلى النشاط تلقائياً. |
| إطلاق مدخرات هدف من هاتفين | يمنع تحرير المبلغ المحجوز مرتين، وتبقى حالة الهدف متسقة بعد الدمج. |

## الغرف مستقبلاً

| السيناريو | القاعدة المطلوبة قبل تنفيذ الغرف |
|---|---|
| عضو يرى بيانات غرفة | يرى فقط ما تسمح به عضوية الغرفة، وليس بيانات الحساب الشخصية الكاملة. |
| عضو يعدل بيانات مشتركة | يظهر صاحب التعديل ووقت التعديل، وتطبق سياسة التعارض نفسها. |
| إزالة عضو أثناء عمله أوفلاين | تمنع التغييرات بعد انتهاء العضوية من الرفع إلى الغرفة. |
| دعوة بريدية لحساب غير مسجل | تبقى الدعوة معلقة ولا تكشف أي بيانات قبل قبولها. |
| حذف الغرفة | يوقف الوصول، مع الاحتفاظ بنسخة مالك الغرفة وفق سياسة الاستعادة. |

## الاختبارات المنفذة

الاختبارات المحلية الموجودة في `tests/sync-scenarios.test.mjs` تغطي: دمج هاتف أوفلاين، دمج الحقول، التعارض الحقيقي، سياسة الحذف، دفعات الديون، واستقرار التقارب بعد المزامنة.

أما حالات انقطاع الشبكة الحقيقي، انتهاء الجلسة أثناء الرفع، وإعادة تثبيت التطبيق فتحتاج اختباراً على جهازين وحساب Supabase مؤقت قبل اعتماد الإصدار الرسمي.
