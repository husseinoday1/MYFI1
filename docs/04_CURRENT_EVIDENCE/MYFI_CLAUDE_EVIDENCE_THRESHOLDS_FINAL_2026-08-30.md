# قرار نهائي — عقد أدلة بصيرة، ردًا على فحص Codex الثالث

**الحالة:** نقاش وقرار نهائي مقترح فقط. لا كود، لا تعديل وثائق مصدرية، لا commit/push.
**يكمّل:** الوثيقة الأولى والملحق، ولا يستبدلهما — هذا الملف هو نقطة التجميع الوحيدة قبل عرضه على مالك المنتج.

تحققتُ من الكود قبل الرد على النقطتين 1 و3 (الأكثر قابلية للتحقق التقني)؛ Codex محق بالثلاث.

---

## 1. عدّ المعاملات يجب أن يُقاس على المصروف المتغير المؤهَّل فقط

**تحقّق:** `variableExpenseSpent` (`src/lib/financialForecast.js:101-109`) **يفلتر فعلًا** بـ`isExpenseFlow(tx) && !isFixedExpenseTransaction(tx, commitments)` عند حساب *القيمة*. لكن `weightedHistoricalVariableSpend` (سطر 138-141) يبني `monthCount`/`baselineMonths` من **وجود أي مفتاح شهر بالفهرس** (`index.monthKeys`)، بلا ربط بنفس فلتر الأهلية. **الفجوة مؤكَّدة بالضبط كما وصفها Codex: عدّ الأشهر لا يستخدم نفس مرشّح القيمة.**

**العقد النهائي:**

```ts
function eligibleVariableSpendCount(
  monthTransactions: Transaction[],
  commitments: Commitment[],
  categoryId?: string,
): number
// = عدد المعاملات التي تحقق isExpenseFlow(tx) && !isFixedExpenseTransaction(tx, commitments)
//   (و tx.cat === categoryId إذا مُرِّر categoryId)
// يُعاد استخدام نفس المُسنِدين (predicates) المستخدمين فعليًا بـ variableExpenseSpent،
// لا منطق فلترة جديد مواز.

function isMonthEligibleForForecast(
  monthTransactions: Transaction[],
  commitments: Commitment[],
): boolean
// = eligibleVariableSpendCount(monthTransactions, commitments) >= 3
```

**"شهر صالح" → "شهر مؤهَّل للتحليل"** كما اقترح Codex بالضبط — التسمية الجديدة تُعتمد بكل الوثائق والواجهة، لأن كل شهر سابق مكتمل زمنيًا فعلًا؛ المشكلة كثافة/ملاءمة البيانات لا التقويم.

**`weightedHistoricalVariableSpend` تُعدَّل** لتبني `baselineMonths` من الأشهر اللي `isMonthEligibleForForecast` تُرجع لها `true` فقط — لا كل مفتاح موجود بالفهرس. `monthCount` المُرجَع يعكس هذا التصفية مباشرة، لا رقمًا منفصلًا يُحسب لاحقًا بالواجهة.

**سلوك فئة بلا مصروف متغير إطلاقًا:** لا تُعامَل كـ"صفر تاريخي" (وهذا يوهم بنمط إنفاق صفري ثابت وهو معلومة كاذبة). بل: **الفئة تُستبعد من حساب `avgTxn` الخاص بها بالبند 2 كليًا**، وتُعامَل بيانات إنفاقها كـ"غير كافية"، لا كـ"صفر".

## 2. لا عتبة عملة احتياطية عند ندرة تاريخ الفئة — أعتمد اقتراح Codex بالكامل

أسحب اقتراحي السابق (عتبة عالمية احتياطية بمنازل العملة) — Codex محق: هذا يعيد جدول عملات مستترًا بعد ما اتفقنا صراحة على رفضه. **لا بديل ذاتي المعايرة أقترحه بدلًا منه — القرار الأصح هو عدم الادعاء أصلًا، لا استبدال عتبة سيئة بأخرى.**

**العقد النهائي:**

```ts
function shouldShowWhyChangedCard(
  category: string,
  currentAmount: number,
  historicalAvgTxn: number | null,  // null = بيانات غير كافية (< 3 أشهر مؤهَّلة، بند 1)
  percentChange: number,
  eligibleTransactionCount: number,
): { show: boolean; reason: 'absolute' | 'relative' | 'insufficient_data' }

// إذا historicalAvgTxn === null:
//     يُعاد { show: false, reason: 'insufficient_data' }
//     — لا بطاقة تلقائية تظهر إطلاقًا. لا استثناء بعتبة مبلغ عالمي.
```

**سلوك الحالة الناقصة (بلا رقم أو تسمية مضللة):** المقارنة الخام (رقمان: الفترة الحالية والمرجعية) **تبقى ظاهرة دائمًا** بالتقرير العادي — هذا مستقل عن بطاقة "لماذا تغيّر" ولا يُخفى أبدًا. فقط **بطاقة التفسير التلقائي** (المصحوبة بحركات/سبب) لا تظهر. إن ضغط المستخدم يدويًا على الفئة لرؤية تفصيل أكثر، تظهر جملة واحدة صريحة:

```
مصروف المطاعم أعلى بـ 85,000 د.ع
نحتاج تاريخًا أكثر لهذه الفئة كي نفسّر التغير بثقة
[عرض حركات هذه الفترة]
```

لا رقم "تقدير" ولا نسبة ثقة مزيّفة — فقط الرقم الخام + الاعتراف الصريح بعدم كفاية البيانات + رابط للتحقق اليدوي.

## 3. بصمة التكرار تحتاج تطبيع الاسم، لا الفئة وحدها

**تحقّق:** `title`/`titleSource` موجودان فعليًا بمخطط الحركة (`src/store/slices/transactionsSlice.js:76-77`) — `titleSource` تكون `'user'` أو `'generated'`. **لا توجد أي دالة تطبيع اسم/تاجر بالمشروع حاليًا** (بحثت، صفر تطابق). هذا يعني: أي بصمة تكرار تعتمد على العنوان تحتاج **دالة تطبيع جديدة بالكامل**، وليست موجودة جزئيًا بمكان آخر يمكن إعادة استخدامه.

**العقد النهائي:**

```ts
function normalizePayeeSignature(title: string, titleSource: 'user' | 'generated'): string | null
// titleSource === 'generated' → يُعاد null فورًا (لا بصمة من عنوان مولَّد تلقائيًا،
//   لأنه ليس اسم تاجر حقيقي — قد يكون نص فئة افتراضي أو "تحويل بين المحافظ").
// titleSource === 'user' → trim + توحيد حالة الأحرف + إزالة أرقام/تواريخ ملحقة شائعة
//   (مثل "نتفليكس #4521" → "نتفليكس")؛ التفاصيل الدقيقة لخوارزمية التطبيع
//   تحتاج عينة بيانات حقيقية قبل التجميد، لا تُقرَّر بهذا المستند.

function detectRecurrenceCandidate(
  transactions: Transaction[],  // معاملات نفس الفئة فقط، كنطاق أولي
): RecurrenceCandidate[]
// يُجمّع المعاملات أولًا بـ normalizePayeeSignature (تُستبعد أي معاملة تُرجع null
// من أي تجميع بصمة)، ثم يُطبَّق كشف الدورة (بند 4 بالملحق السابق) **داخل كل
// مجموعة بصمة على حدة**، لا على الفئة كاملة.
// معاملة واحدة بلا بصمة صالحة (عنوان مولَّد) لا تدخل أي مرشح تلقائي؛
// تبقى مرئية بالسجل العادي فقط.
```

**عندما لا توجد بصمة موثوقة (عنوان مولَّد أو تطبيع غير حاسم):** الاقتراح **لا يُسمّى اكتشافًا تلقائيًا إطلاقًا**. يبقى الخيار الوحيد: المستخدم يربط يدويًا حركتين متشابهتين بنفسه من واجهة صريحة ("اربط هذه بدفعة سابقة")، ويُنشئ النظام مرشح الدورة **من رابط المستخدم اليدوي نفسه**، لا من تخمين آلي. هذا **مطابق حرفيًا** لما اشترطته الوثيقة الأصلية (`MYFI_FINANCIAL_TRACKER_BUILDER_FUTURE_DESIGN`) بخصوص التعرف التلقائي كاقتراح مراجَع لا حقيقة.

## اختبارات قبول سلبية (تمنع الأخطاء الثلاثة تحديدًا)

```text
1. شهر فيه 3 حركات: تحويل بين محفظتين + دفعة دين + تسوية رصيد
   (صفر معاملات مصروف متغير مؤهَّلة)
   ⇒ isMonthEligibleForForecast = false
   ⇒ لا يُحتسب ضمن monthCount، ولا يرفع مستوى ثقة التوقع.

2. فئة "مطاعم" بمعاملتين فقط بتاريخها الكامل (كلاهما بشهر واحد)
   ⇒ avgTxn = null (بيانات غير كافية، بند 1: يحتاج 3 أشهر مؤهَّلة لا 3 معاملات بشهر واحد)
   ⇒ shouldShowWhyChangedCard يُعيد { show: false, reason: 'insufficient_data' }
   ⇒ المقارنة الخام تظهر، بطاقة "لماذا تغيّر" لا تظهر.

3. حركتان بنفس الفئة ("مطاعم")، بفاصل زمني يطابق نافذة شهرية،
   لكن العنوانان مختلفان جوهريًا وبتطبيع صريح مختلف
   (title="مطعم الأصالة" مقابل title="ستاربكس")، كلاهما titleSource='user'
   ⇒ normalizePayeeSignature يُنتج بصمتين مختلفتين
   ⇒ detectRecurrenceCandidate لا يجمعهما بنفس المجموعة
   ⇒ صفر مرشح تكرار تلقائي؛ لا اقتراح اشتراك خاطئ.
```
