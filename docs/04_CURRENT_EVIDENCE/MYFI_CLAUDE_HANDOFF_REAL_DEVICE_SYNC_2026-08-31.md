# MYFI — هاندأوفر الاختبار الفعلي والمزامنة

**التاريخ:** 2026-08-31  
**الحالة:** تقرير أدلة فقط. لا يحتوي هذا الملف على تغيير سحابي أو قرار دمج أو طلب دفع.

## الغرض

هذا يلخّص ما حدث بعد آخر مراجعات Claude: بناء APK من GitHub Actions، اختبار فعلي على هاتف أندرويد، نجاحات مؤكدة، وعطل مزامنة مالي مانع اكتُشف بعد إجراء إعادة ضبط محلية. لا يعتمد التقرير على لقطات شاشة محفوظة؛ لقطات الفحص المؤقتة التي احتوت معلومات حساب حُذفت.

## 1. البناء والجهاز

- جرى بناء APK من GitHub Actions بنجاح (Run #17، العمل `P10-014A Normal MYFI APK`).
- الـAPK مبني من commit `2c6dae3959585bfbe1033329c590fa9868dc1741` على الفرع `fix/pui-001-r2-onboarding-reader-recent-transactions`.
- ثُبّت على هاتف أندرويد حقيقي عبر USB debugging. هذا ليس محاكيًا.
- لا تخلط نتائج الهاتف مع التغييرات المحلية اللاحقة المذكورة في §4؛ الـAPK لم يكن يحتويها.

## 2. ما تأكد فعليًا على الهاتف

| المسار | النتيجة | ملاحظة |
| --- | --- | --- |
| إنشاء حساب وتأكيد البريد | نجح | عدم وصول الرسالة في المحاولة الأولى كان لأن الحساب موجود أصلًا. بعد إزالة الحساب الاختباري القديم من Supabase وإعادة التسجيل وصل التأكيد وعمل التسجيل. |
| تسجيل الدخول | نجح | الحساب الفعلي أصبح متصلًا. |
| إنشاء مصروف | نجح | سُجلت حركة بقيمة اختبارية، وظهرت في السجل. |

| إغلاق التطبيق وفتحه | نجح قبل إعادة الضبط | لم يظهر فقدان فوري للبيانات المحلية في المسار العادي. |
| حذف الحركة من السجل | مقصود ونجح | غياب الحركة بعد ذلك **ليس** دليل فقدان بيانات أو فشل استعادة؛ المستخدم حذفها عمدًا. |

### ملاحظة البريد والهوية

رسالة التأكيد حاليًا مرسلة من مزود Supabase. قرار المنتج هو أن تُرسل لاحقًا بهوية MYFI ونطاق MYFI وبريد مرسل مخصص. لا يوجد نطاق معتمد بعد، كما أن تغيير اسم المنتج أُضيف للخطة. هذا عمل هوية/بنية بريدية منفصل، وليس إصلاحًا لسبب تعذر التسجيل الأول.

## 3. عطل حقيقي مانع: `financial_v2_revision_conflict`

### إعادة الإنتاج الفعلية

1. تسجيل الخروج.
2. استخدام إجراء «حذف البيانات المحلية» داخل التطبيق.
3. تسجيل الدخول مجددًا.

بعدها بقيت واجهة الحساب في وضع **Needs attention / offline / dirty**، وسجل التطبيق أظهر:

```text
[P20_V2_MUTATION_STATE] {
  protocol: 2,
  ok: false,
  reason: "financial_v2_revision_conflict",
  uploaded: 0,
  downloaded: 0,
  pendingAfterSync: 0
}
```

هذا ليس خطأ شبكة عابرًا؛ تكرر بعد المحاولة، ولا ينبغي معالجة ذلك بإعادة المحاولة أو بإخفاء الخطأ في الواجهة.

### ما تحقق من السحابة (قراءة فقط)

- رؤوس مراجعات الكيانات السحابية مطابقة للحركات المتاحة؛ لا توجد علامة تلف في البيانات السحابية نفسها.
- يوجد Bootstrap V2 نهائي وتفاصيله ورؤوسه موجودة ومتسقة.
- لذلك مصدر التعارض هو انتقال الحالة المحلية بعد إعادة الضبط، لا السجل السحابي.

### السبب المرجح والمؤيد مباشرة بالكود

المساران التاليان يجتمعان بصورة غير آمنة:

1. `src/store/slices/dataSlice.js` في `resetAll` يسمح بالحذف عندما يكون المستخدم مسجل الخروج، لأن القفل يختبر `current.user && current.financialLedgerV7Cutover` فقط. بعد الحذف يعيد إنشاء إعداد مالي فارغ/محفظة افتراضية ويجعل الحالة `dirty`.
2. `clearFinancialWorkspaceV7` في `src/lib/financialLedgerV7Repository.js` يمسح صفوف V7 الأساسية، لكنه لا يمسح أو يعيد تهيئة هوية V8 النشطة (`ledger_sync_identity_v8`) وسجل/حالة V2 (`ledger_outbox_v3` و`ledger_sync_state_v8`).
3. `runVerifiedEmptyShellCloudRecoveryV2` في `src/store/slices/useSyncSlice.js` يرجع مبكرًا عند وجود V2 نشط مع shell فارغ (`financial_v2_already_active`) قبل جلب الـBootstrap السحابي النهائي.
4. يوجد كود يكتشف أن استيراد Bootstrap V2 مطلوب (`financial_v2_bootstrap_import_required`) لكنه لا يملك منفذ استيراد كامل فعليًا؛ الموجود هو bootstrap **رفع** محلي، لا استعادة bootstrap نهائي إلى SQLite.

المحصلة: حالة إعداد محلية جديدة تتعامل مع هوية ومراجعات سحابية قديمة، فتصل إلى `financial_v2_revision_conflict`.

### القرار المطلوب قبل أي بناء جديد

لا يجوز شحن إصلاح تجميلي. نحتاج مسارًا واحدًا محددًا ومختبرًا:

- **الخيار المفضل:** «حذف البيانات المحلية» لا ينشئ أي outbox أو setup state مالي جديد. عند تسجيل الدخول يعيد استيراد Bootstrap V2 الموثق إلى SQLite ثم يبدأ المزامنة، أو يعرض حالة استعادة صريحة غير قابلة للكتابة حتى يكتمل الاستيراد.
- **الحد الأدنى المؤقت الآمن:** امنع الإجراء حتى عند تسجيل الخروج إذا كان namespace يحمل V2 نشطًا، مع نص يشرح أن الاستعادة السحابية لهذا المسار غير جاهزة. هذا يمنع خلق تعارض، لكنه ليس بديلًا طويل الأجل للاستعادة.

لا ينبغي أن يعني «حذف البيانات المحلية» حذف النسخة السحابية أو التقدم بعصر الاستعادة السحابي تلقائيًا؛ ذلك يغير عقد المنتج ويحتاج موافقة منفصلة.

### اختبارات قبول لازمة للإصلاح

1. حساب V2 مع Bootstrap نهائي + حركة محفوظة: تسجيل خروج → حذف محلي → دخول → استعادة نفس الحركة بلا conflict.
2. حساب V2 فارغ لكن له wallet/category bootstrap: نفس التسلسل بلا outbox متعارض ولا حالة `dirty/offline` دائمة.
3. إعادة تشغيل التطبيق بعد الاستعادة: لا يعاد bootstrap أو يكرر إرسال أي حركة.
4. حذف حركة مقصود ثم إعادة الضبط المحلي: تبقى الحركة محذوفة ولا تعود من السحابة.
5. حالة سلبية: أي فشل تحقق للـBootstrap يبقي البيانات للقراءة فقط مع رسالة قابلة للتشخيص، ولا ينشئ تغييرات محلية تُرفع.

## 4. إصلاح محلي غير مودع: المحفظة عند وجود محفظة واحدة

ظهر على الهاتف أن واجهة الدخل/المصروف لا تعرض المحفظة عندما توجد محفظة واحدة. السبب:

```js
modules.wallets && walletList.length > 0
```

في تخصيص شخصي قد تكون `modules.wallets` مخفية، لكن تظل هناك محفظة افتراضية حقيقية يجب أن يفهم المستخدم أين ستُسجل الحركة.

الإصلاح المحلي الحالي في:

- `src/components/AddTransModal.js`
- `tests/ui-contract.test.cjs`

سلوكه:

- محفظة واحدة: بطاقة ثابتة واضحة باسم المحفظة ووسم «المحفظة الوحيدة المتاحة» أو «المحفظة الافتراضية»، بلا منتقي مضلل.
- أكثر من محفظة: يظهر المنتقي المعتاد.

التحقق المحلي المنجز:

```text
npm run test:ui           -> passed
npm run test:gate:static  -> 73 passed, 0 failed, 11 skipped
```

هذه التغييرات غير مودعة عمدًا ولم تُدفع، ولا توجد في APK الذي اختبر على الهاتف.

## 5. اقتراح «حذف النسخة السحابية»

طلب مالك المنتج إضافة زر مستقبلي لحذف البيانات السحابية. هذا **ليس منفذًا** الآن، ويجب عدم دمجه ضمن معنى «حذف البيانات المحلية».

العقد المقترح للنقاش:

- إجراء منفصل عن حذف الحساب وعن حذف الجهاز.
- تأكيد مزدوج + إعادة مصادقة.
- يوقف المزامنة ويمنع الرفع التلقائي بعد المسح؛ لا يجوز أن تعود البيانات من الهاتف بلا اختيار واضح من المستخدم.
- لا يحذف بيانات الهاتف تلقائيًا.
- إعادة النسخ إلى السحابة تكون فعلًا مستقلًا: «استخدم بيانات هذا الجهاز كنسخة سحابية جديدة».
- يحتاج سجل تدقيق، معالجة أجهزة متعددة، وتنفيذًا خادميًا آمنًا.

## 6. ما لا ينبغي استنتاجه

- لا يوجد دليل من الاختبار على فقدان حركة عبر logout/login؛ الحركة المعنية حُذفت عمدًا قبل الفحص.
- لا يوجد دليل أن السحابة فاسدة؛ العكس، فحص الاتساق يدعم أن المشكلة انتقال حالة محلية.
- لا نطلب بناء APK آخر قبل معالجة هذا التعارض واختبارات الاستعادة، لأن البناء الحالي صالح لاكتشاف العطل لكنه لا يمكنه إثبات إصلاحه.

## 7. طلب مراجعة Claude

راجِع التشخيص والترتيب المقترح، خصوصًا:

1. هل توجد تبعيات V2/restore epoch لم يلتقطها المسار أعلاه؟
2. هل تفضل تنفيذ مستورد Bootstrap V2 كاملاً الآن، أم قفل آمن مؤقت مع خطة استيراد واضحة؟
3. اقترح اختبار runtime حقيقي (لا عقد نصي) يحاكي logout → local reset → login على SQLite مع مصدر bootstrap موثق.
4. راجع فصل «حذف البيانات المحلية» عن «حذف النسخة السحابية» كي لا يؤدي أي UI قادم إلى حذف أو إعادة رفع غير مقصودين.
