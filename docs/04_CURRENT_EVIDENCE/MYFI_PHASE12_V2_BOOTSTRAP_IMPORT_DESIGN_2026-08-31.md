# MYFI Phase 12 — تصميم استيراد Bootstrap V2 الكامل

**الحالة:** تصميم للمراجعة فقط — لا كود، لا ترحيل قاعدة بيانات، ولا تغيير في بيانات المستخدم.

**التاريخ:** 2026-08-31
**المالك التنفيذي:** Codex
**المراجع المطلوب:** Planning & Audit / Claude
**الأولوية:** مانع سلامة بيانات قبل أي ميزة كبيرة جديدة.

## 1. القرار الذي يعالجه هذا التصميم

ثبت اختبار جهاز حقيقي مسارًا خطيرًا: بعد تسجيل الخروج ثم حذف البيانات المحلية، يمكن أن يبقى على الجهاز أثر هوية ومزامنة V2، بينما يُمسح السجل المالي V7. عند تسجيل الدخول من جديد، يرى التطبيق حالة V2 موجودة محليًا ويختصر الاستعادة، ثم لا يجد سجلًا محليًا صالحًا لمقارنته بالسحابة. النتيجة كانت تعارض مراجعة `financial_v2_revision_conflict` وظهور الحالة `offline/dirty` بدل استعادة سليمة.

الإصلاح المؤقت الموجود في commit `cf758f1` يمنع الحذف المحلي غير الآمن. لكنه **لا يستعيد** البيانات الموجودة أصلًا، ولا يحل حالة جهاز جديد أو تطبيق أعيد تثبيته. الحل الدائم هو مستورد Bootstrap V2 مخصص، ينسخ النسخة السحابية النهائية المتحقق منها إلى SQLite بصورة ذرية، ثم يفعّل المزامنة بالطريقة العادية.

## 2. الحقائق الثابتة التي يبنى عليها

1. SQLite على الجهاز هي الحقيقة التشغيلية؛ السحابة نسخة مزامنة/استعادة، وليست مكانًا يسمح للتطبيق بالدمج التخميني.
2. Bootstrap V2 السحابي موجود بالفعل، نهائي وغير قابل للتعديل بعد الإنهاء، ويمكن قراءته عبر `get_financial_bootstrap_rows_v2` للمستخدم المالك فقط.
3. صفوف Bootstrap الحالية موثقة بالترتيب وببصمة لكل صف وبـmanifest شامل: `currency`، `account`، `exchange_rate`، `financial_transaction`، `posting`، `transaction_link`، `entity`، `workspace_state`.
4. التحقق السحابي القائم يتحقق من الهوية، الترتيب، مفاتيح الصفوف، JSON، SHA-256، العدد، وبصمة الـmanifest. يجب إعادة استخدامه أو استخراج قارئ مشترك منه، لا كتابة تحقق ثانٍ مختلف.
5. آلية V11 لاستعادة نسخة احتياطية محلية تملك staging/promotion مفيدة كنمط، لكن لا يجوز استعمالها مباشرة: استيراد Bootstrap V2 ليس "استعادة نسخة يدوية" ولا يجوز له زيادة `restoreEpoch` أو إنشاء baseline سحابي جديد.
6. وجود V2 محلي لا يثبت أن المحتوى المحلي ما زال مطابقًا للسحابة. لا يجوز بعد الآن أن يكون `financial_v2_already_active` سببًا لتجاوز فحص مصدر الاستعادة عندما تكون مساحة العمل صدفةً فارغة أو متضررة.

## 3. النطاق وما هو خارج النطاق

### داخل النطاق

- تنزيل Bootstrap V2 النهائي المملوك للمستخدم والتحقق منه قبل لمس SQLite الحية.
- staging محلي خاص ومتين، وإثبات مطابقته رياضيًا للنسخة السحابية.
- ترقية ذرية إلى مساحة العمل الحية ثم استئناف منسق V2 القائم للتحقق والمزامنة الظلية.
- استئناف آمن بعد إغلاق التطبيق/انقطاع الشبكة، مع واجهة واضحة لا تغيّر أموال المستخدم بصمت.
- اختبار SQLite فعلي + تحقق سحابي تجريبي + قبول على جهازين.

### خارج النطاق عمدًا

- دمج قيمي بين سجل محلي وسحابي متعارض.
- إعادة العمل ببروتوكول V1 أو الرجوع إلى legacy snapshot بعد وجود Bootstrap V2 نهائي.
- إعادة رفع Bootstrap أو تعديل سجل السحابة أثناء الاستيراد.
- حذف سحابي، حذف حساب، أو زر "استخدم هذا الجهاز كنسخة سحابية جديدة"؛ هذه قرارات مستقلة ذات تأكيدات صريحة.
- تنفيذ ميزات كبيرة مثل MYFI Flow أو صانع المتابعات قبل إغلاق Phase 12.

## 4. شروط الأهلية: متى يظهر مسار الاستعادة

لا يبدأ الاستيراد إلا إذا اجتمعت الشروط التالية:

1. جلسة مستخدم صالحة ومطابقة لمالك المصدر السحابي.
2. فحص محلي read-only يثبت أن المساحة الحية **empty shell**، لا مجرد رصيد صفر. الفحص يشمل صفوف V7 المالية، هوية V2، outbox V3، sync state V8، و`ledger_v7_meta` المرتبط بالحالة المالية.
3. لا توجد كتابة مالية جارية، ولا import/restore آخر، ولا حساب آخر داخل نفس التطبيق.
4. مصدر `v2_bootstrap` مكتشف من RPC القراءة فقط ومكتمل metadata: `ledgerId` و`epoch` و`bootstrapId` و`expectedRows` و`manifestSha256`.
5. لا توجد علامة استيراد مكتمل محليًا تثبت أن نفس المصدر موجود ومطابق للحي.

حالة الحساب الطبيعي الذي لم يسجل أي بيانات فعلًا لا يجب أن يمر باستيراد متكرر: يمكن اعتباره سليمًا فقط عندما يوجد receipt محلي مطابق للمصدر أو برهان حي يعيد بناء الـmanifest نفسه. دون أحدهما، يعامل كحالة تحتاج تحققًا لا كحالة "نشطة" تلقائيًا.

## 5. مسار الاستيراد المقترح

### A. قفل الصيانة والاكتشاف

1. يفتح التطبيق حالة صيانة قصيرة: يوقف الكاتب المالي والمزامنة والـoutbox، ويحفظ snapshot للجلسة الحالية.
2. يقرأ مصدر التعافي عبر RPC فقط، ثم يتحقق أن المصدر V2 نهائي ومملوك لنفس المستخدم.
3. ينشئ Import Session محليًا مع بصمة المصدر فقط، لا مع payload مالي كامل في السجلات أو logs.

### B. تنزيل وتحقق مستقلان عن السجل الحي

1. ينزّل الصفحات بالترتيب من RPC القائم.
2. القارئ المشترك يرفض فورًا: JSON غير صالح، ordinal مفقود أو مكرر، نوع صف غير مسموح، row key مكرر أو غير متوقع، SHA خاطئ، عدد غير مطابق، أو manifest مختلف.
3. لا يكتب أي صف في namespace الحي في هذه المرحلة.
4. يكتب الصفوف المقبولة فقط إلى namespace مرحلي خاص لا يملك outbox ولا هوية sync فعالة.

### C. إثبات المرحلة

قبل الترقية، يثبت المستورد كل الآتي:

- `foreign_key_check` و`quick_check` في SQLite.
- كل علاقة بين posting / transaction / account / entity / rate / link صحيحة ولا يوجد repair صامت لمحفظة أو عملة أو مرجع مفقود.
- إعادة قراءة المرحلة ثم إعادة إنشاء canonical rows والـmanifest تعطي بالضبط نفس المصدر السحابي.
- projection دلالي: الأرصدة، العملات وأسعارها، الحركات، القيود، الروابط، الكيانات، وإعداد الحالة تطابق المصدر؛ لا يكفي تشابه عدد الصفوف.
- لا تفعّل المرحلة بروتوكول V2 ولا تنشئ أوامر سحابية.

### D. إعادة تحقق قبل الترقية

فور اكتمال الإثبات، يعيد التطبيق اكتشاف المصدر. يجب أن تكون هوية السجل، epoch، bootstrap ID، عدد الصفوف، والـmanifest كما كانت عند البداية. كذلك يجب أن تبقى الجلسة ونفس empty-shell proof صالحين. أي اختلاف يلغي الترقية ويبقي الحي كما هو.

### E. الترقية الذرية

تجري كلها داخل معاملة SQLite واحدة:

1. يعاد فحص أن الحي empty shell؛ إذا وصلت حركة جديدة أو تغيّر الحساب، تفشل المعاملة بلا overwrite.
2. تمسح **كل** أسطح حالة V2 المتصلة بالمساحة الحية ضمن قائمة مسماة ومراجعة، لا صفوف V7 وحدها: الصفوف المالية، أوامر V3 المتراكمة، حالة المزامنة، هوية الربط السابقة عند لزوم إعادة الربط، bootstrap state، وmetadata المالية V7 الخاصة بالهوية القديمة. لا تمسح metadata عامة أو schema لمجرد الراحة.
3. تنسخ صفوف المرحلة المثبتة إلى namespace الحي.
4. تربط الهوية المحلية بـ`ledgerId` و`epoch` السحابيَّين باستخدام compare-and-set، وفقط إذا كانت الهوية السابقة خاملة/غير مربوطة ولا يوجد namespace آخر مرتبط بالسجل نفسه.
5. تثبت receipt: مصدر Bootstrap المستورد وmanifest وبصمة الإثبات وحالة `imported_activation_pending`.
6. لا تضع `activated_at` هنا، ولا تزيد restore epoch، ولا تنشئ outbox، ولا ترسل أي كتابة للسحابة.
7. تحذف بيانات المرحلة والجلسة أو تعلّمها مكتملة داخل المعاملة نفسها بحسب حاجة سجلات التدقيق.

بعد commit، يعاد تحميل مساحة العمل من SQLite ثم يستدعى منسق V2 القائم بوضع "import evidence": يتحقق من المصدر نفسه، يبدأ من cursor آمن، يمزج deltas اللاحقة مرة واحدة، ويعلن التفعيل فقط عند quiescence الموجودة في عقد V2.

## 6. تصميم الحالة الدائمة والاستئناف

الجدول الحالي `ledger_bootstrap_import_state_v8` مرتبط FK بهوية V2 (`ledger_sync_identity_v8`). هذا يمنعه من تمثيل مرحلة قبل إعادة ربط هوية جهاز فارغ بالمصدر السحابي من دون كسر ترتيب الأمان. التوصية هي **جدول Import Session جديد ذي إصدار مستقل**، وليس التحايل على FK الحالي.

الحد الأدنى للـsession:

| الحقل | الغرض |
|---|---|
| namespace محلي + session ID | يمنع تصادم عمليتين |
| user ID hash / owner binding | يمنع استئناف جلسة مستخدم آخر |
| ledger ID + epoch + bootstrap ID | يثبت المصدر |
| expected rows + manifest SHA | رابط التحقق الدقيق |
| phase (`download`, `proved`, `promotion_pending`, `activation_pending`, `failed`) | استئناف آمن |
| timestamps + سبب فشل غير حساس | تشخيص دون تسريب بيانات مالية |
| stage namespace / proof hash | يربط المرحلة بالبرهان |

سلوك الإقلاع بعد crash:

- قبل الترقية: يستأنف أو يحذف المرحلة بعد إعادة تنزيل/تحقق؛ الحي لا يتغير.
- أثناء الترقية: SQLite rollback يعيد كل الطبقات كما كانت.
- بعد الترقية وقبل activation: لا ينشئ Bootstrap جديدًا ولا يعيد النسخ؛ يثبت المصدر ثم يكمل activation فقط.
- تغيير مستخدم أو انتهاء جلسة: يوقف العملية؛ لا ترقية ولا استئناف تلقائي على حساب آخر.

## 7. فجوة يجب حسمها قبل الكود: cold archive

مرحلة Bootstrap V2 الحالية لا تحتوي صفوف cold archive ضمن الأنواع الثمانية؛ كما أن قارئ مرحلة bootstrap الحالي لا يقرأها. Phase 12 يشترط استعادة دلالية لكيانات الأرشيف أيضًا.

لذلك لا يجوز أن نسمي هذا المسار "استعادة مالية كاملة" قبل قرار صريح لأحد خيارين:

1. **توسعة Bootstrap بإصدار بروتوكولي جديد:** تضيف أنواع archive اللازمة ومخطط التحقق والترحيل السحابي، مع توافق واضح للـBootstrap الموجود سابقًا.
2. **تحديد عقد منتج أضيق:** Bootstrap V2 يستعيد الدفتر الحي فقط، أما الأرشيف فله مسار backup مستقل واضح للمستخدم ولا يدّعي التطبيق استعادته من السحابة.

التوصية: الخيار الأول إذا كان الأرشيف جزءًا من وعد الاستعادة عبر الحساب. لا نضيفه ضمن المستورد بصمت، لأن ذلك يغيّر manifest وواجهة SQL وتوافق السجلات الموجودة.

## 8. نقاط تقنية تحتاج إثباتًا قبل التنفيذ

1. **حالة cursor في التفعيل محسومة جزئيًا من الكود القائم:** `activateFinancialSyncProtocolV2V8` يشترط أن يكون `last_server_sequence = 0` قبل التفعيل، ويسجل `validationCursor` منفصلًا كدليل shadow validation. إذًا لا ينشئ المستورد cursor إنتاجيًا جديدًا ولا يختار قيمة بديلة. ما يبقى لإثبات 12-B/12-D هو كيف يحسب `validationCursor` من المصدر، وأن بدء الإنتاج من صفر لا يعيد baseline أو delta أكثر من مرة.
2. ما قائمة مفاتيح `ledger_v7_meta` الدقيقة التي تعد مالية ومتصلة بالهوية؟ يجب تسميتها واختبارها؛ لا delete واسع.
3. كيف يميّز empty-shell proof "حساب جديد فارغ فعلًا" من "مساحة محذوفة محليًا"؟ receipt/manifest proof هو الحل المقترح، ويحتاج اختبارًا واضحًا.
4. هل الـBootstrap يتضمن كل data domains التي تظهر في الواجهة الحالية، خصوصًا archived data؟ بند 7 هو مانع الإغلاق.
5. هل يوجد منع سحابي من الربط المتزامن لنفس ledger إلى namespace محلي ثانٍ؟ إن لم يوجد، يضاف قيد محلي وجلسة جهاز واضحة دون منع تعدد الأجهزة المشروع.

## 9. تجربة المستخدم

لا تظهر المصطلحات التقنية أو أرقام السجلات للمستخدم. التسلسل المقترح:

1. **"وجدنا نسخة أموالك المحفوظة"** — زر: "استعدها على هذا الجهاز"، مع عبارة أن البيانات الحالية على الجهاز فارغة ولا سيجري التحقق قبل الاستعادة.
2. **"نتحقق من سلامة النسخة"** — لا تعرض نسبة وهمية؛ المراحل الحقيقية: تنزيل، تحقق، تجهيز، مزامنة.
3. عند النجاح: **"عادت أموالك، ونتحقق من أحدث التغييرات"** ثم لا تعلن الاكتمال إلا بعد activation/quiescence.
4. عند أي فشل: **"توقفت الاستعادة لحماية بياناتك. لم نغيّر بيانات هذا الجهاز."** مع إعادة محاولة وتفاصيل دعم غير حساسة.

للحالة الموجودة الآن (جهاز عالق بعد الحذف) لا ننفذ استعادة صامتة عند صدور الميزة؛ نظهر هذا المسار بعد أن يثبت empty-shell، أو نطلب من المستخدم تأكيد الاستعادة إذا كانت هناك أي بيانات محلية قابلة للتفسير.

## 10. أرضية الاختبار المطلوبة

### اختبارات runtime على SQLite حقيقية

لا تكفي اختبارات نصية. تُنشأ قاعدة SQLite حقيقية، مصدر Bootstrap وهمي موثق، ثم تقرأ الجداول بعد كل حالة.

| الحالة | النتيجة الإلزامية |
|---|---|
| Bootstrap كامل | تطابق row/manifest ودلالي بعد الترقية ثم activation |
| hash أو manifest خاطئ | لا يتغير الحي |
| row ordinal مفقود/مكرر أو JSON غير صالح | لا يتغير الحي |
| type غير معروف أو reference مفقود | لا repair ولا تغيير حي |
| metadata مصدر تغيرت قبل promotion | إلغاء آمن |
| تغيير مستخدم/جلسة أثناء التنزيل | إلغاء آمن |
| كتابة محلية قبل promotion | إلغاء بلا overwrite |
| crash عند كل حد معاملة | snapshot قاعدة البيانات قبل/بعد متطابق أو promotion كامل مرة واحدة |
| import ثانٍ للمصدر نفسه | لا duplicates ولا Bootstrap جديد |
| delta سحابي بعد Bootstrap | يطبق مرة واحدة فقط بعد activation |
| عيب في أحد أسطح V2 الأربعة | لا يسمح reset/import بنصف حالة |

عينة baseline يجب أن تحتوي، حيث يدعم العقد الحالي: محافظ متعددة العملات وأسعار تحويل وتقييم تاريخي، حركات وpostings وروابط، دين وهدف والتزام وميزانية وتكرار وtracker type/item. archive يدخل بعد حسم بند 7.

### تحقق سحابي تجريبي

- حساب A لا يستطيع قراءة Bootstrap حساب B (RLS/RPC).
- مصدر finalized يعود ثابتًا وبنفس manifest عبر الصفحات.
- المستورد لا ينفذ أي RPC كتابة قبل activation ولا ينشئ Bootstrap جديدًا.

### قبول أجهزة حقيقية

بحساب اختبار فقط:

1. جهاز A: ينشئ محافظ/حركات من العينة، يتأكد من وصولها للسحابة.
2. جهاز B أو تطبيق cleared storage: يسجل الدخول ويستعيد عبر Bootstrap؛ لا نستعمل بعد الآن زر حذف محلي لتجاوز interlock.
3. قطع الشبكة خلال التنزيل، إغلاق التطبيق قبل promotion، ثم فتحه: لا فقد ولا duplicate.
4. تغيير بعد baseline على جهاز A، ثم تحقق أن جهاز B يأخذ delta واحدة.
5. فحص الأرصدة، المحافظ، التقارير والمتابعات في الواجهة، لا صفوف SQL فقط.

## 11. قرار مالك المنتج: الأرشيف جزء من الاستعادة الكاملة

اعتمد مالك المنتج في 2026-08-31 أن استعادة الحساب تشمل الأرشيف البارد، لا الدفتر الحي فقط. لذلك لا يجوز لواجهة الاستعادة أن تدّعي "اكتملت" إذا لم يعد الأرشيف كذلك.

### قيد التوافق المكتشف في 12-A

جلسات Bootstrap السحابية المنتهية مصممة لتكون immutable: صفوفها وmanifestها لا تتغير بعد `finalized`. كما أن نوع الصفوف في migration الحالي محصور بالأنواع الثمانية ولا يحتوي archive. لذلك لا يمكن إضافة archive إلى Bootstrap قديم موجود من دون كسر بصمته، أو تعديل سجل سحابي اعتبره البروتوكول نهائيًا.

هذا يعني أن "أضف archive إلى Bootstrap" لا يكفي وحده؛ يجب اختيار طريقة انتقال للسجلات الموجودة قبل النسخة الجديدة:

| الخيار | النتيجة | المخاطرة/الكلفة |
|---|---|---|
| A. Bootstrap protocol جديد + controlled re-baseline | كل حساب يحصل لاحقًا على baseline جديد شامل archive | يتطلب عملية سحابية تغيّر العهد وتنسيقًا كاملًا بين الأجهزة؛ لا يبدأ قبل تصميم مستقل وموافقة صريحة |
| B. قناة archive موثقة مستقلة مرتبطة بالـBootstrap | الاستعادة تجمع baseline المالي القديم مع archive الموثق، بلا تعديل Bootstrap القديم | يحتاج جداول/RPC/manifest archive وproof ذري، لكنه لا يعيد كتابة تاريخ الـBootstrap |
| C. دعم archive للحسابات الجديدة فقط | أسهل تنفيذًا | غير مقبول كمنتج: الحسابات القديمة لن تحصل على استعادة كاملة |

**التوصية التنفيذية:** الخيار B للحسابات ذات Bootstrap النهائي القائم، ثم تضمين archive rows في نسخة Bootstrap التالية للحسابات الجديدة فقط. بهذه الطريقة نفي بوعد الاستعادة الكاملة من دون إعادة رفع baseline نهائي أو رفع restore epoch من جهاز جديد. لا نختار A أو نبدأ migration له من دون قرار مالك منتج منفصل، لأنه عملية استعادة سحابية وليست توسعة واجهة.

## 12. مراحل التنفيذ بعد المراجعة

كل مرحلة commit محلي مستقل، ولا push أو APK من دون موافقة صريحة جديدة.

1. **12-A:** اعتماد البروتوكول، حسم cold archive، وتحديد اشتقاق `validationCursor` واختباره، وتصميم Import Session migration.
2. **12-B:** قارئ/متحقق Bootstrap نقي مع اختبارات SQLite سلبية شاملة، بلا ترقية.
3. **12-C:** staging durable وproof دلالي وcrash-resume، بلا لمس للحي.
4. **12-D:** atomic promotion/rebind مع fault injection واختبار الأسطح الأربعة.
5. **12-E:** دمج منسق V2، UX، وactivation pending.
6. **12-F:** سحابة تجريبية + قبول جهازين + توثيق دليل الإغلاق. عندها فقط يعاد تقييم interlock المؤقت؛ لا يزال يبقى fail-closed إذا لم يتوفر الاستيراد.

## 13. طلب مراجعة Claude

يرجى مراجعة هذا التصميم مقابل الكود والعقود، خصوصًا:

1. هل فصل Import Session الجديد عن `ledger_bootstrap_import_state_v8` ضروري بسبب FK فعلًا، أم توجد طريقة آمنة ومدعومة لترقية الجدول الحالي؟
2. هل قائمة أسطح V2 التي يجب أن تنظف/تعاد ربطها كاملة، وبالأخص `ledger_v7_meta`؟ نحتاج قائمة مفاتيح لا وصفًا عامًا.
3. هل cursor بعد import يمكن إثباته من بروتوكول SQL الحالي؟
4. هل cold archive مستبعد من Bootstrap فعلًا، وأي خيار من بند 7 يحمي وعد المنتج؟
5. هل توجد حالة تعارض أو crash لم تغطها مصفوفة الاختبار؟
6. هل تنصح بتأكيد مستخدم دائم حتى عندما يثبت empty-shell، أم استعادة تلقائية صامتة بعد تسجيل الدخول؟

لا يبدأ التنفيذ قبل إغلاق هذه الملاحظات وحسم بند الأرشيف والـcursor.

## 14. نتيجة مراجعة آلية Restore Epoch القائمة

تحققنا من `beginLedgerRestoreEpochV8` و`advanceLedgerRestoreEpochInTransactionV8` و`activateFinancialSyncProtocolV2V8`. النتيجة ليست "إعادة بناء كل شيء" ولا "إعادة استعمال الآلية كاملة"؛ بل إعادة استعمال دقيقة لما يناسب العقد، ومنع ما لا يناسبه.

### ما نعيد استخدامه

- **`readLedgerRestoreIntentV8`:** بوابة منع. إذا كان restore intent حقيقيًا قائمًا، لا يبدأ import جديد ولا promotion.
- **`runFinancialRestorePromotionTransactionV8` أو طبقة المعاملة الحصرية المكافئة:** بعد مراجعة API الفعلي، تستعمل كحد تنفيذ ذري للـpromotion بدل فتح معاملة ثانية مستقلة.
- **عقد التفعيل القائم:** `activateFinancialSyncProtocolV2V8` هو التفعيل الوحيد. يثبت أن الإنتاج يبدأ و`last_server_sequence = 0` وأن `validationCursor` دليل منفصل؛ لا نبني تفعيلًا ثانيًا.

### ما لا يجوز إعادة استخدامه في Bootstrap import

`beginLedgerRestoreEpochV8` و`advanceLedgerRestoreEpochInTransactionV8` صمما لاستعادة تغيّر العهد نفسه، لا لاستيراد baseline موجود من عهد سحابي قائم:

1. `beginLedgerRestoreEpochV8` قفل **محلي داخل SQLite** في `ledger_v7_meta`، وليس قفلًا سحابيًا بين جهازين. لا يمكنه وحده منع جهاز ثانٍ جديد من بدء عملية مستقلة.
2. `begin...` يستدعي `ensureShadowLedgerSyncIdentityV8`؛ هذه تنشئ هوية محلية عشوائية عند غيابها. ذلك مخالف لمسار جهاز جديد يجب أن يربط نفسه أولًا بـ`ledgerId` السحابي المعتمد، لا يولّد ledger محليًا جديدًا.
3. `advance...` يشترط هوية قائمة ثم يزيد `restoreEpoch` من `N` إلى `N+1`. Bootstrap المصدر النهائي يخص ledger وعهدًا سحابيًا موجودين بالفعل؛ زيادة العهد محليًا ستنتج mismatch حتى تجري عملية سحابية تغيّر العهد أيضًا.
4. تغيير العهد السحابي هو عملية restore مختلفة تمامًا، تعزل أوامر العهد السابق وتحتاج إثباتًا وحدثًا سحابيًا. استيراد Bootstrap لا يجب أن يكتب إلى السحابة أو يلغي تاريخ الأجهزة الأخرى، ولذلك لا يجوز له استدعاء هذه العملية.

إضافة `bootstrap_v2_import` إلى قائمة operations وحدها لا تحل هذه الفروقات؛ ستعطي اسمًا جديدًا لآلية ما زالت تزيد العهد وتحتاج هوية محلية مسبقة.

### قفل التزامن بين جهازين

التزامن المحلي يحميه Import Session + المعاملة الحصرية. أما جهازان مختلفان فلا يحميهما meta محلي. لا نحتاج server lock يغيّر epoch لأن العملية read-only حتى الترقية المحلية؛ يمكن لجهازين تنزيل نفس Bootstrap الثابت بأمان. الخطر الحقيقي هو تفعيل/تطبيق delta. لذلك يجب أن يثبت اختبار الجهازين أن كل جهاز يربط نفس `ledgerId/epoch` ويستعمل idempotency/cursors الموجودة، بلا رفع epoch ولا إنشاء baseline ثانٍ. إذا كشف هذا الاختبار تعارضًا سحابيًا فعليًا، نضيف lease سحابيًا جديدًا مستقلاً ومحدودًا للاستيراد، لا نسيء استخدام Restore Epoch.

### تعديلات مقبولة من مراجعة Claude

- يبقى جدول Import Session الجديد ضروريًا بسبب FK في `ledger_bootstrap_import_state_v8`.
- توسعة Bootstrap لتشمل cold archive هي التوصية، لكنها قرار مالك المنتج قبل التنفيذ.
- تضاف لاختبارات القبول: جهازان يستوردان المصدر نفسه، وحالة false-positive لكاشف empty shell مع تحقق دفاعي لاحق يمنع overwrite.
- سياسة UX: تثبيت جديد بلا تاريخ محلي يمكن أن يستعيد تلقائيًا؛ أي جهاز يحمل دليل استعمال سابق يحتاج تأكيد المستخدم قبل promotion.
