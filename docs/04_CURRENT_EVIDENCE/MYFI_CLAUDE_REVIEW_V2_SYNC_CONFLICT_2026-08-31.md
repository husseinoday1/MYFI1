## 0. الحكم المختصر

**التشخيص دقيق بالكامل، تحققت من كل سطر كود ذُكر.** هذا عطل حقيقي مانع بأرضية التحقق (Verification Floor)، لا وهمًا. أضفت اكتشافًا واحدًا لم يذكره التقرير: جدول/مفاتيح رابعة غير مُنظَّفة تغذّي نفس الخلل. إجاباتي على الأسئلة الأربعة بالأسفل، مع توصية واضحة لسؤال 2.

## 2. اكتشاف إضافي — جدول/مفاتيح رابعة لم يذكرها التقرير

تتبعتُ `readFinancialSyncProtocolV8` (`financialLedgerV7Repository.js:1498-1537`) — الدالة اللي تُنتج `existingProtocol.activeProtocolVersion` المستخدَم بالفحص المبكر (البند أعلاه). هي تستدعي:

- `ensureLedgerSyncIdentityV8` — يقرأ/يُنشئ صف `ledger_sync_identity_v8` (نفس الجدول غير المُنظَّف).
- استعلامين مباشرين على **`ledger_v7_meta`** بمفاتيح مربوطة بـ`ledgerId`/`restoreEpoch` القديمين تحديدًا (`activationEvidenceKey`, `legacyActivationEvidenceKey`, `epochActivationPendingKey`).

**`ledger_v7_meta` أيضًا غير مذكور بقائمة `clearFinancialWorkspaceV7` المُنظِّفة.** يعني: حتى لو أُضيفت الجداول الثلاثة اللي ذكرها Codex (`ledger_sync_identity_v8`/`ledger_outbox_v3`/`ledger_sync_state_v8`) لمنطق التنظيف، **مفاتيح أدلة التفعيل بـ`ledger_v7_meta` المرتبطة بالهوية القديمة تبقى، وتُعاد قراءتها بنفس الدالة اللي تسبب الفحص المبكر الخاطئ.** أي إصلاح حقيقي يحتاج تنظيف **أربعة مواضع، لا ثلاثة.**

## 3. إجابات الأسئلة الأربعة

### س1 — تبعيات V2/restore epoch لم يلتقطها المسار المذكور؟

**نعم، واحدة محددة:** `ledger_v7_meta` بمفاتيح الأدلة/التفعيل المعلَّقة (`activationEvidenceKey`/`epochActivationPendingKey`) — مفصَّلة أعلاه بالقسم 2. أي إصلاح يجب يشمل تنظيف هذي المفاتيح بنفس namespace/ledgerId القديم، لا الاكتفاء بالجداول الثلاثة المذكورة بالتقرير الأصلي.

**نقطة ثانية تستحق تحققًا قبل التنفيذ (لم أستطع تأكيدها بالكامل بوقت المراجعة):** `clearFinancialWorkspaceV7` يستدعي `advanceActiveFinancialGenerationInTransactionV13` عند مسح صفوف. هل "الجيل المالي" (`financial generation`) هذا مرتبط بـ`restoreEpoch` بـV8، أم مفهوم منفصل كليًا؟ إذا مرتبط، فقد يكون هناك تفاعل ثالث يستحق تتبعًا قبل قفل التصميم النهائي للإصلاح — أطرحه كسؤال فحص إضافي لـCodex، لا كادعاء مؤكَّد مني.

### س2 — مستورد Bootstrap V2 كامل الآن، أم قفل آمن مؤقت مع خطة استيراد؟

**التوصية: القفل الآمن المؤقت الآن، بلا تردد، والمستورد الكامل كمشروع منفصل بعده مباشرة — لا بالتوازي ولا مؤجَّلًا.**

**السبب:**
1. **القفل صغير ومفهوم بالكامل** — توسيع نفس الشرط الموجود بـ`dataSlice.js:220` ليشمل حالة تسجيل الخروج مع هوية V8 نشطة محليًا، بدل الاعتماد فقط على `current.user`. هذا تعديل بسطر واحد تقريبًا بمنطق مألوف، خطر التنفيذ منخفض جدًا.
2. **المستورد الكامل كود كتابة مالية جديد بالكامل** — يحتاج نفسه دورة تحقق كاملة (استيراد صفوف V7 من Bootstrap، إعادة بناء هوية V8، معالجة تعارضات جزئية، اختبارات تكامل SQLite حقيقية) قبل الوثوق فيه. شحنه الآن تحت ضغط "نغلق العطل بسرعة" **بالضبط النمط اللي حذّرنا منه طول هذي الجلسة** (شحن كود مالي جديد بلا وقت تحقق كافٍ).
3. **الأولوية الفعلية الآن هي منع الضرر، لا استرجاع كل قدرة الاستعادة فورًا.** القفل يمنع أي مستخدم حقيقي من الوقوع بنفس التعارض بدءًا من اللحظة اللي يُشحن فيها، بينما المستورد الكامل يستغرق وقتًا أطول ليكون آمنًا فعلًا للشحن.

**هذا يتوافق تمامًا مع توصيتي بجلستنا قبل قليل بخصوص Phase 12** — هذا العطل **دليل مباشر وملموس** على إن جولة النسخ الاحتياطي/الاستعادة الكاملة لسا غير مغلقة فعليًا، بالضبط الفجوة اللي حذّرت منها. المستورد الكامل هو بالضبط عمل Phase 12 المتبقي، لا ميزة جانبية.

### س3 — اختبار runtime حقيقي (لا عقد نصي) لمحاكاة logout → local reset → login

**المخطط المقترح (وصف منطقي، لا كود — كما طُلب بهذي الجولة):**

```text
1. تهيئة SQLite حقيقية (نفس هارنس الجهاز الموجود فعليًا:
   src/dev/financialLedgerV7DeviceHarness.js) بـnamespace اختباري.
2. إنشاء هوية V8 + كتابة حركة حقيقية عبر مسار الأمر الفعلي (insertCommandWithoutOutbox
   أو المسار العادي)، ثم تفعيل بروتوكول V2 (activeProtocolVersion = 2) فعليًا
   بنفس الدوال المستخدَمة بالإنتاج — لا محاكاة/mock للحالة.
3. تجهيز "مصدر سحابي" ثابت (fixture): تمثيل Bootstrap V2 نهائي موثَّق
   (ledgerId + restoreEpoch + صفوف الحركة نفسها) — يُمرَّر لـ
   fetchVerifiedFinancialCloudRecoverySourceV2 عبر استبدال مصدر البيانات
   باختبار (test double)، لا استدعاء Supabase حقيقي.
4. تنفيذ resetAll({ maintenanceOwned: true }) بحالة current.user = null
   (محاكاة تسجيل خروج فعلي أولًا) — هذا يُشغِّل clearFinancialWorkspaceV7
   الحقيقية على قاعدة SQLite الحقيقية، لا محاكاة.
5. تسجيل دخول (تعيين current.user من جديد)، ثم استدعاء
   runVerifiedEmptyShellCloudRecoveryV2 الحقيقية.
6. التأكيد: النتيجة ليست financial_v2_already_active ولا
   blocked_v2_bootstrap_import — بل استيراد فعلي يُعيد الحركة الأصلية
   لقاعدة SQLite، يُتحقَّق منه بقراءة الصفوف مباشرة من القاعدة
   (لا من حالة store بالذاكرة)، مطابقة تامة للحركة الأصلية.
```

**الفارق الجوهري عن عقد نصّي:** كل خطوة تُشغِّل الدالة الحقيقية على قاعدة SQLite حقيقية (ولو مؤقتة/اختبارية)، لا تفحص وجود نص بالكود المصدري. هذا يطابق نمط `tests/financial-core.test.mjs` المستخدَم فعليًا هذي الجلسة (`useStore.getState().addTrans(...)` حقيقي، لا محاكاة) — أوسّعه هنا ليشمل طبقة SQLite نفسها، لا طبقة الـstore فقط، لأن العطل هنا بطبقة القاعدة تحديدًا.

### س4 — فصل «حذف البيانات المحلية» عن «حذف النسخة السحابية»

**أوافق على عقد Codex المقترح (§5) بالكامل**، وأضيف شرطًا تقنيًا واحدًا مباشرًا من نفس هذا التشخيص: **حين تُبنى «حذف النسخة السحابية» لاحقًا، يجب أن تتجنب نفس فئة الخطأ بالاتجاه المعاكس** — أي: أي حذف سحابي جزئي (يمسح بعض الجداول السحابية ويُبقي أخرى) سينتج نفس نوع التعارض من جهة الخادم بدل الجهاز. **قاعدة القبول لكلا الإجراءين يجب تكون واحدة:** "حذف" يعني إما مسحًا كاملًا متسقًا لكل الطبقات (هوية + محتوى + حالة مزامنة) أو لا شيء إطلاقًا — لا حالة وسطى تُبقي بعض الطبقات قديمة وبعضها جديدة، **وهذا بالضبط السبب الجذري للعطل الحالي.**

كذلك: **القفل المؤقت المقترح بالسؤال 2 هو فعليًا الحد الفاصل الصحيح بين الإجراءين** — طالما لا يوجد مستورد استعادة كامل موثوق، "حذف البيانات المحلية" لا يجوز أن يُسمح له أصلًا بالتعامل مع حالة تحمل هوية V2 نشطة، بغض النظر عن حالة تسجيل الدخول. هذا يمنع بنيويًا تكرار الالتباس بين الإجراءين لحين اكتمال «حذف النسخة السحابية» كإجراء منفصل موثَّق.
